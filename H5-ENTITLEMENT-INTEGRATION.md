# Satchel H5 subscription and allowance integration

Satchel's online content and its entitlement rules are owned by the H5 and provider backend. The native app does not control H5 video playback or downloads. A successful Apple transaction by itself is not a B-side entitlement: the app creates a provider order, sends the verified transaction and receipt to `rights-order/buySuccess`, and only then returns `purchased`. H5 should request `subscription.getStatus` after purchase and use the current visitor's provider status (`rightExpireTime`) to refresh access. Backend verification, renewal, expiry and refund handling must keep that status current; these server behaviors have not been verified here. Do not grant permanent access merely because a socket message says `purchased`.

## Product configuration

- A and B use the same Apple products: `coins_1.99` (monthly) and `conis_4.99` (yearly). The spelling of `conis` is intentional. Configure these exact IDs in H5, the provider backend, and Satchel's own Apple app. The ID strings do not set prices; the current intended prices remain USD 9.99/month and USD 99.99/year, and Apple supplies the actual displayed price.
- H5 `subscription.getProducts` receives Apple product details; `subscription.purchase` uses the returned `planId`. The existing `pay` action uses `params.plan` of `monthly` or `yearly`. Transaction source is identified by a persisted purchase token, not by product ID. A verified shared Apple entitlement also unlocks the A-side; B-side rights still require the provider to confirm the corresponding B-side order. An A-side purchase does not automatically create a B-side order.
- An unfinished transaction whose source token is unavailable is left for reconciliation rather than being claimed by either side. The B-side ledger is local; restoring it on a different device or after reinstall is not guaranteed and needs provider-side reconciliation.
- The current `getV2` integration defines no product-ID field, so changing IDs on the backend alone does not automatically change the app. Align `PortalConfiguration` when the provider supplies other IDs. Existing purchase records keep their original ID for reconciliation.
- Purchases require the provider's `NB01` purchase switch and iOS receipt-verification settings to be present and enabled, as well as Apple products configured for Satchel. The last observed demo response did not contain the required values; its current configuration has not been rechecked.

## Clipo-based H5 rights to implement with the H5 team

For an active provider membership, the Clipo reference grants unlimited views, unlimited downloads, and media export. Clipo also skips app-open ads for verified members; Satchel currently keeps startup ads as explicitly requested, so that exception is not copied. H5/backend must apply membership and enforce any content access themselves.

For non-members, Clipo's local defaults are 5 views and 5 downloads per day; provider configuration may override the base limits. A repeat view on the same day and a repeat download of an already downloaded item do not spend another allowance. Watching a completed rewarded ad for the corresponding exhausted allowance adds 3 views for each of the first three view rewards, or 5 downloads for each download reward. The fourth completed ad for that allowance makes that allowance unlimited until the daily reset. View and download reward counters are separate. Clipo resets the daily counters at 05:00 UTC. Clipo also has a local no-fill courtesy allowance that does not advance ad progress; Satchel's existing H5 ad result reports failure when no reward was earned, so any equivalent courtesy is an H5/backend product decision and must not be reported as an SDK reward.

H5 should credit an ad-based reward only once per request after an actual `rewarded` result. The native app reports `rewarded` only on the Google SDK reward callback. It reports failures and dismissals separately. The relay's ACK confirms receipt, not a verified purchase or an ad reward. The precise forwarded product-query and restore message shapes, backend entitlement updates, and successful end-to-end behavior still require coordination and verification with the provider.
