# Satchel

A local-first SwiftUI travel journal and packing companion. The Xcode project is `Satchel.xcodeproj`; `project.yml` is its XcodeGen source.

## Project materials

- `ProjectMaterials/DesignReferences`: reference designs and notes.
- `ProjectMaterials/UIAssets`: original generated Satchel artwork and source images.
- `ProjectMaterials/ContentImages`, `ProjectMaterials/ContentVideos`: optional supplied content.

Only `Satchel/Assets.xcassets` and `Satchel/Resources` are configured as app resources. The material folders are not included in the app target. The original artwork was created using the host-native image tool for this project, including the travel cover, sign-in scene, satchel illustration, paper ticket, app icon, and navigation illustrations.

The A-side uses the selected Sea Window icon, an original coastal hero, and custom blue-and-ivory button and navigation artwork. Journeys and journal entries can be searched by destination or memory text, memories can be added from the journal overview, packing can be filtered to remaining items, and the new-trip form previews the chosen cover. These changes preserve the existing on-device trip data and the separate online-service entry. The Travel guide is an offline, locally scripted feature with prepared topic-based responses; it does not call an AI service or provide live information.

## Online service

At startup the app automatically requests a guest session and `getV2` package configuration. A valid `NB02` opens the H5 directly; a missing or invalid address, login/configuration failure, or initial H5 navigation failure falls back to the local travel journal. The A-side Me screen retains the in-app legal documents and a manual online-service retry. The native login and H5 continue to use the existing provider endpoints. No fixed H5 host list is required. Browsing permits HTTP or HTTPS addresses; App Transport Security may block insecure HTTP content. The H5 has no direct native JavaScript bridge; the authenticated WebSocket handles the documented purchase, ad, and subscription messages while the online page is open. The provider confirmed that product-query and restore requests are forwarded through the server; their actual message format still requires integration verification.

The provider's development HTTP and WebSocket host is `devapi.io-jp.com`; the returned H5 is hosted on `devjackiu.io-jp.com`. `releaseName` uses the iOS example `iaptest.ios`. The currently served H5 reads the visitor ID from its URL, so the app adds the signed-in visitor ID to `NB02` without adding its access token. The WebSocket uses the logged-in user ID and access token; do not log the full connection URL.

An authenticated HTTP 401 triggers one shared guest-login refresh and one retry, provided the returned visitor ID is unchanged. A token refresh reconnects the active WebSocket; a WebSocket handshake visibly returning HTTP 401 also attempts one refresh. Whether the server exposes that handshake status through URLSession and the full reconnection behavior still require live verification.

Google Mobile Ads and User Messaging Platform are declared as Swift packages. The sample application ID and official iOS test app-open, rewarded and interstitial ad units are used. App-open is attempted on cold startup while the loading screen is visible. The startup watchdog allows up to 15 seconds of foreground preparation, pauses while the consent flow is in progress and resets that allowance after it, and skips an unavailable ad when no consent flow is active. If the consent update fails, a previous session's consent is used only when UMP says ads may be requested. Console logs under the app's `AppOpenAd` category record preparation, timeout, errors by stage and impression without logging credentials. H5-triggered ads share the same presentation manager. A-side reward and interstitial placements are not included in this iteration. Reward is reported only when the SDK issues its reward callback. AdMob production app ID, production ad units, SKAdNetwork configuration, privacy messages, and associated disclosure must be completed and validated before release.

The online purchase path uses the shared product IDs `coins_1.99` (monthly) and `conis_4.99` (yearly), creates an order before StoreKit, and submits the receipt to `buySuccess`. The two IDs are centralized in `SubscriptionProductIDs`; align changes with H5, the provider backend and Apple configuration. They are not read from `getV2`: the supplied contract does not establish a product-ID field. A and B share the products but associate purchases with their source using separate durable token records. Each new operation persists its actual product ID; records from older versions retain the original demo mapping. New purchases are blocked when `NB01` disables them or the receipt verification configuration is missing. The last observed test `getV2` response contained neither `NB01` nor the iOS receipt-verification configuration, so purchases were blocked before order creation. The app reports `purchased` only after backend confirmation. Records are associated with the visitor and a StoreKit app-account token; unfinished transactions without a matching record are not claimed or finished. A pending purchase keeps its original `requestId` for a later result. The operation ledger is local and survives page recreation; no purchase is automatically repeated after an uncertain order. The provider confirmed repeated verification will not issue the same entitlement twice, so the app retries verification of the same order and transaction, including when the page or socket reconnects. H5 acknowledges results with an `ACK` containing `userId`, `requestId`, `platform: h5`, `action`, `status: received`, and `version: 1`. The app accepts both a direct ACK and the relay-wrapped form, and retains unacknowledged operations for redelivery. Since this ACK does not identify the result status, a request that has sent more than one status (such as pending followed by purchased) or has unknown legacy send history remains eligible for redelivery rather than treating an ambiguous ACK as confirmation of the latest result. An ACK carrying `receivedStatus` can identify the matching status. A successful socket send by itself does not prove H5 receipt. The test relay currently accepts an app connection without a token and forwards its results, so an ACK or socket result alone is not authenticated evidence of purchase or reward. Product queries use StoreKit's actual localized product data. Restore returns `purchased` only when a verified StoreKit entitlement matches this visitor's previously verified local B-side record and the backend reports an unexpired entitlement; otherwise it returns `pending`. It does not force an Apple account sign-in from a remote command. H5 queries the provider's current entitlement through the app; server-side renewal and refund update behavior is not established by that query. The connection and unfinished-transaction recovery run while the online page is open. See `H5-ENTITLEMENT-INTEGRATION.md` for the Clipo-based H5 rules and integration responsibilities.

## Membership

The A and B test product IDs are `coins_1.99` (monthly) and `conis_4.99` (yearly). Configure these exact IDs for Satchel's own app in App Store Connect, in one subscription group; the current intended prices remain USD 9.99/month and USD 99.99/year. The ID spelling does not determine price, and the app displays the price returned by Apple. Existing A-side entitlements for `satchel.plus.monthly`, `satchel.plus.yearly`, `clipo.plus.monthly`, and `clipo.plus.yearly` remain recognized. A shared verified Apple entitlement unlocks the A-side; B-side rights require provider confirmation of a B-side order, and an A-side purchase does not automatically create one. A purchase tokens are stored before StoreKit begins so the A observer does not finish an unknown B-side transaction. Unknown-source unfinished transactions remain pending for reconciliation, and reinstall or device migration can lose the local ownership records. The free plan allows 3 trips and 30 photos; active members have unlimited trips and photos. Existing records remain viewable and exportable after expiry. The export is JSON with Base64-encoded local photos; an import workflow is not implemented.

`Satchel.storekit` and the separate `Satchel Local StoreKit` Xcode scheme prepare the shared products and legacy A-side products in one group, plus historical B-side demo products in a separate group for record continuity. The earlier scheme launch on 2026-10-29 did not load the products; no local purchase or restore was performed. The updated configuration has not been run. Payment testing is deferred. Local StoreKit transactions are not App Store sandbox transactions and do not establish that the provider can verify a receipt.

The development bundle identifier is a placeholder. Select the real bundle identifier and signing team before distribution. Supply the operator’s contact details, confirm the online provider’s data-retention and account-deletion process, and publish a privacy policy before release. The app contains local English terms and privacy policy drafts displayed in WebView; these need review and final publication.

## Storage and verification

Journal data and photos are stored in the app's local application-support directory. Removing the app may remove those records. Sign-in uses a Keychain device identifier and a session token held in memory.

On 2026-10-29, Xcode 27.1 built and ran the app in the iPhone 18 Pro iOS 27.0 simulator. Tourist login, H5 loading, the WebSocket payment-request/failure-result round trip, and Google test interstitial and rewarded ads were exercised. The test ads returned `dismissed` and `rewarded`, respectively, and the simulated H5 acknowledged both results. The H5 video displayed “Video unavailable”. No successful StoreKit purchase, backend receipt verification, complete restore, physical-device, accessibility, localization-layout, or Duo posture validation has been run.
