# Satchel

A local-first SwiftUI travel journal and packing companion. The Xcode project is `Satchel.xcodeproj`; `project.yml` is its XcodeGen source.

## Project materials

- `ProjectMaterials/DesignReferences`: reference designs and notes.
- `ProjectMaterials/UIAssets`: original generated Satchel artwork and source images.
- `ProjectMaterials/ContentImages`, `ProjectMaterials/ContentVideos`: optional supplied content.

Only `Satchel/Assets.xcassets` and `Satchel/Resources` are configured as app resources. The material folders are not included in the app target. The original artwork was created using the host-native image tool for this project, including the travel cover, sign-in scene, satchel illustration, paper ticket, app icon, and navigation illustrations.

The A-side uses the selected Sea Window icon, an original coastal hero, and custom blue-and-ivory button and navigation artwork. Journeys and journal entries can be searched by destination or memory text, memories can be added from the journal overview, trips can be marked as favorites and filtered on the trips screen, packing can be filtered to remaining items, and the new-trip form previews the chosen cover. Favorites are stored with each trip and included in JSON exports. These changes preserve the existing on-device trip data. The Travel guide is an offline, locally scripted feature with prepared topic-based responses; it does not call an AI service or provide live information.

## Online service

At startup the app requests a guest session and `getV2` package configuration before loading the configured app-open ad. A valid `NB02` starts loading the H5 behind the launch screen. After the ad has finished or been skipped, the same WebView is revealed when the initial navigation finishes or when the committed document has visible text or a loaded image. A missing or invalid address, login/configuration failure, initial H5 navigation failure, or no initial content within 30 foreground seconds falls back to the local travel journal. This early-content check does not establish that H5 business data has loaded. The H5 container extends under the status and home-indicator areas, without automatic scroll-view safe-area insets; the H5 itself is responsible for its content and control placement. The A-side Me screen retains the in-app legal documents and does not offer a manual online-service entry. The native login and H5 continue to use the existing provider endpoints. No fixed H5 host list is required. Browsing permits HTTP or HTTPS addresses; App Transport Security may block insecure HTTP content. The H5 has no direct native JavaScript bridge; the authenticated WebSocket handles the documented purchase, ad, and subscription messages while the online page is open. The provider confirmed that product-query and restore requests are forwarded through the server; their actual message format still requires integration verification.

The configured provider HTTP API is `https://u9v8kve.satchel.click` and the WebSocket host is `u9v8kve.satchel.click`. The Satchel release configuration uses `name=Satchel` and returns the H5 address in `NB02`. The production login, release configuration, WebSocket and H5 payment flow still require end-to-end verification. The request sends the device's time-zone identifier; it does not assume the example's Tokyo time zone or Gboard keyboard. The app adds only the same `deviceCode` used for guest login and `appId` from the actual app bundle identifier to `NB02`. Existing values for those two query parameters are replaced; other returned query parameters are preserved. The WebSocket uses the logged-in user ID and access token; do not log full connection URLs or the device code. H5 loading and its handling of these parameters still require runtime verification.

An authenticated HTTP 401 triggers one shared guest-login refresh and one retry, provided the returned visitor ID is unchanged. A token refresh reconnects the active WebSocket; a WebSocket handshake visibly returning HTTP 401 also attempts one refresh. Whether the server exposes that handshake status through URLSession and the full reconnection behavior still require live verification.

Google Mobile Ads and User Messaging Platform are declared as Swift packages. The packaged AdMob app ID is configured for Satchel. App-open and rewarded unit IDs come from `getV2` `adList` types 1 and 5; the Google advertiser, app ID, publisher ID, unit ID format, and a unique matching entry must validate before use. Missing or invalid configuration never falls back to a test ad. App-open is attempted on cold startup after the configuration is available. The existing startup watchdog allows up to 15 seconds of foreground preparation, pauses while the consent flow is in progress and resets that allowance after it, and skips an unavailable ad when no consent flow is active. If the consent update fails, a previous session's consent is used only when UMP says ads may be requested. H5 rewarded requests return failure when configuration is unavailable and report a reward only after the SDK reward callback. Interstitial ads are not configured; an H5 interstitial request receives a failure. The provider must return valid production placements, and SKAdNetwork configuration, privacy messages and the resulting ad flows still require validation.

The online purchase path uses the shared product IDs `com.satchel.traveljournal.monthly` (monthly) and `com.satchel.traveljournal.yearly` (yearly), creates an order before StoreKit, and submits the receipt to `buySuccess`. The two IDs are centralized in `SubscriptionProductIDs`; align changes with H5, the provider backend and Apple configuration. They are not read from `getV2`: the supplied contract does not establish a product-ID field. A and B share the products but associate purchases with their source using separate durable token records. Each new operation persists its actual product ID; records from older versions retain the original demo mapping. New purchases require a successfully loaded release configuration and are blocked when `NB01` is true or has an unrecognized type. A missing or null `NB01` permits purchasing. The provider confirmed that `sandBoxTest` and `iosVerifyShareKey` are configured server-side, so the app omits them from `buySuccess`; backend verification must still succeed before access is reported as purchased. The app reports `purchased` only after backend confirmation. Records are associated with the visitor and a StoreKit app-account token; unfinished transactions without a matching record are not claimed or finished. A pending purchase keeps its original `requestId` for a later result. The operation ledger is local and survives page recreation; no purchase is automatically repeated after an uncertain order. The provider confirmed repeated verification will not issue the same entitlement twice, so the app retries verification of the same order and transaction, including when the page or socket reconnects. H5 acknowledges results with an `ACK` containing `userId`, `requestId`, `platform: h5`, `action`, `status: received`, and `version: 1`. The app accepts both a direct ACK and the relay-wrapped form, and retains unacknowledged operations for redelivery. Since this ACK does not identify the result status, a request that has sent more than one status (such as pending followed by purchased) or has unknown legacy send history remains eligible for redelivery rather than treating an ambiguous ACK as confirmation of the latest result. An ACK carrying `receivedStatus` can identify the matching status. A successful socket send by itself does not prove H5 receipt. The test relay currently accepts an app connection without a token and forwards its results, so an ACK or socket result alone is not authenticated evidence of purchase or reward. Product queries use StoreKit's actual localized product data. Restore returns `purchased` only when a verified StoreKit entitlement matches this visitor's previously verified local B-side record and the backend reports an unexpired entitlement; otherwise it returns `pending`. It does not force an Apple account sign-in from a remote command. H5 queries the provider's current entitlement through the app; server-side renewal and refund update behavior is not established by that query. The connection and unfinished-transaction recovery run while the online page is open. See `H5-ENTITLEMENT-INTEGRATION.md` for the Clipo-based H5 rules and integration responsibilities.

## Membership

The A and B product IDs are `com.satchel.traveljournal.monthly` (monthly) and `com.satchel.traveljournal.yearly` (yearly). Configure these exact IDs for Satchel's own app in App Store Connect, in one subscription group; the planned prices are USD 9.99 per month and USD 99.99 per year; subscription periods and prices must be configured and verified in App Store Connect. The backend usdPrice values must be checked against the configured subscription prices and the provider contract before release. The ID spelling does not determine price, and the app displays the price returned by Apple. Existing A-side entitlements for `satchel.plus.monthly`, `satchel.plus.yearly`, `clipo.plus.monthly`, and `clipo.plus.yearly` remain recognized. A shared verified Apple entitlement unlocks the A-side; B-side rights require provider confirmation of a B-side order, and an A-side purchase does not automatically create one. A purchase tokens are stored before StoreKit begins so the A observer does not finish an unknown B-side transaction. Unknown-source unfinished transactions remain pending for reconciliation, and reinstall or device migration can lose the local ownership records. The free plan allows 3 trips, 30 photos, and one travel-guide question per local calendar day; active members have unlimited trips, photos, and questions. The daily question count is stored on the device. Existing records remain viewable and exportable after expiry. The membership screen uses the subscription period and price returned by StoreKit; it does not infer the period from an ID. Restore purchases is available in the Me screen. The export is JSON with Base64-encoded local photos; an import workflow is not implemented.

The shared Satchel scheme has no local StoreKit configuration. Product details are requested from the App Store; TestFlight and App Review purchases use Apple's sandbox. App Store Connect product configuration and a complete sandbox transaction still need to be verified separately.

The development bundle identifier is a placeholder. Select the real bundle identifier and signing team before distribution. Supply the operator’s contact details, confirm the online provider’s data-retention and account-deletion process, and publish a privacy policy before release. The app contains local English terms and privacy policy drafts displayed in WebView; these need review and final publication.

## Storage and verification

Journal data and photos are stored in the app's local application-support directory. Removing the app may remove those records. Sign-in uses a Keychain device identifier and a session token held in memory.

On 2026-10-29, Xcode 27.1 built and ran the app in the iPhone 18 Pro iOS 27.0 simulator. Tourist login, H5 loading, the WebSocket payment-request/failure-result round trip, and Google test interstitial and rewarded ads were exercised. The test ads returned `dismissed` and `rewarded`, respectively, and the simulated H5 acknowledged both results. The H5 video displayed “Video unavailable”. No successful StoreKit purchase, backend receipt verification, complete restore, physical-device, accessibility, localization-layout, or Duo posture validation has been run.

While the B-side page is open, unfinished transactions are rechecked every 30 seconds as well as on socket reconnection. If a receipt is missing during a user-initiated purchase, the app requests a receipt refresh before retrying confirmation; Apple may ask the user to authenticate. Payment requests retain `pending` locally without sending it to H5; only confirmed `purchased`, `cancelled`, or `failed` outcomes are sent. Uncertain transactions remain unfinished for reconciliation, so a final result cannot be guaranteed immediately. A failed socket send triggers reconnection so persisted results can be retried. `PortalPayment` logs record the confirmation stage, HTTP and business status codes, result-send status and H5 ACK without logging receipts, tokens or full URLs. A socket send is not proof that the H5 received or processed the result. On 2026-11-05, the test H5 source disabled the payment timeout and retained the request through `pending` and socket reconnects; live behavior and app-restart recovery have not been verified.

If StoreKit returns a verified transaction whose account token does not match the new B-side order, the app does not associate that transaction with the new order or report a successful purchase. An existing B-side record for the same user may be reconciled against its own original order; unknown or different-user transactions remain unfinished. The new H5 request remains unresolved until its own purchase can be established.
